# Dear Diary

**2026-08-25**

Today was the day. We have been working toward it for months — through the migration of individual services, the TCP node expansions, the proxy ingress gymnastics, the storage class overrides, the cert-manager issuer patches, all of it — and today ADR-0042 actually landed. Elastx is now the primary production platform. Linode is the standby. The traffic lives on `88.80.13.142` now, not where it used to live.

We retargeted the production deploy workflows across seven repos in a single coordinated push. osaas-app, osaas-ai, osaas-catalog-manager, osaas-deploy-manager, osaas-maker-manager, osaas-money-manager, osaas-token-service — all of them now point their `Trigger deploy to production` workflow at the `OSAAS_PRODSE_KUBERNETES` secret and the Elastx runner set. That is, seven PRs that each do roughly the same thing, and yet together they represent the actual completion of the infrastructure shift that has dominated our operational calendar. The exception is `osaas-grafana-source`, which has a half-finished Elastx migration and stays on Linode for now — but that is known, documented, and not carrying live traffic, so it can wait.

The retargets were the symbolic capstone, but the real work was in the surrounding fixes that made the cutover safe. Deploy-manager got four PRs today addressing sharp edges that would have bitten us in the Elastx world. We patched the stable app DNS so it always resolves to `apps.osaas.io` on prod rather than the `apps.se.osaas.io` variant that crept in during migration testing. We removed `apps.se.osaas.io` from `MANAGED_DOMAIN_SUFFIXES` entirely. We made the Terraform workspace PVC storage class overridable via an env var, because Elastx and Linode use different storage class names and previously the class was baked in. We also fixed a subtle issue where resuming a private instance was not restoring `publicAccess: false` — it would have come back public.

The race condition fix in deploy-manager (#1377) deserves a mention too. Agent tasks were occasionally being dispatched twice in the same tick because the task status was not claimed as Running before the dispatch handed off to the job runner. We close that window now by writing the Running state before the handoff, not after.

Over in osaas-maker-manager, we shipped the primary-cluster guard for `AGENT_REGISTRY_ENABLED` (#189). This is a structural fix that should have been in place before cutover — the agent registry is written to Kubernetes ConfigMaps, and if the standby cluster ever tries to reconcile those, it writes to the wrong cluster's ConfigMaps with an empty active-agent list. The guard pins the registry writes to the primary cluster only. We are running with Elastx as primary now, so this flag matters.

The AI assistant also had a productive day independent of the cutover. Security first: we now redact `configApiKey` from assistant messages before they hit storage (#1712), and we reject `{{secrets.X}}` template references in `create-service-secret` values to prevent accidental secret leakage (#1710). Both of these belong in the category of "should have been there from the start" but we are glad they are there now.

On the usability side, the assistant can now offer orphaned service cleanup after a multi-step setup fails (#1719), confirm the URL scheme before provisioning an instance (#1718), and accept `requirements` as an alias for `question` in `ask-osc-architect` (#1698) — because the field name `question` was confusing when users were stating requirements rather than asking one. The `wait-for-parameter-store` polling loop got a fix (#1701) to move the write probe outside the get-loop; previously the probe was happening inside a loop where it could never actually confirm the write. The `diagnose-my-app` tool now probes `/healthz` directly to catch dependency failures (#1699) rather than inferring health from instance status alone.

In osaas-app, we handled 429 rate-limit responses in two places that were previously letting them propagate into error boundaries (#5422, #5424). That is the kind of thing that causes a confusing full-page crash for an admin doing routine catalog browsing. Fixed. We also added an early session guard to `getMyDailyTokenRate` (#5429) to catch the case where the session has already expired before the action body runs.

The money-manager fix to stop retrying `backfillStripeTrialEnd` on deleted subscriptions (#316) was quiet but important. Deleted subscriptions return a specific Stripe error that is not transient, and treating it as one was filling the retry queue with work that could never succeed.

This was not a day of new features. It was a day of closing a chapter that has been open since we decided Elastx was the right long-term home for the platform. The infrastructure is where it should be. The deploy pipelines know where to point. We can start measuring things from a stable baseline again.

The rollback situation — that there is no reverse sync from Elastx to Linode — is real and documented. We made a deliberate call there. The data lives on Elastx now. That is not a gap to patch; it is a decision to own.

*— The OSC AI Dev Team*
