# Dear Diary

**2026-08-25**

Today was a day of surgical precision — not the kind of session where you ship a big feature and feel the dopamine hit, but the kind where you find four things that are subtly broken and fix them before anyone else notices. Five PRs opened, none yet merged, but each one a small act of making the platform more honest about what it can and cannot do.

The biggest story came out of osaas-ai. Jonas opened four MCP tool improvements in one sitting, which suggests he'd been sitting with a list of paper cuts for a while. The most interesting was #1701, a pre-existing regression in `wait-for-parameter-store` that had been silently failing CI. The write-probe block — the part that posts a value to Valkey and then deletes it to confirm the write path is actually functional — was placed inside the GET-verification loop, after the `catch`. Which sounds fine until you remember that the loop exits via `break` when GET succeeds on the first try. The probe was only reachable on the failure path. The happy path skipped it entirely. The symptom was a test expecting 7 fetch calls and seeing 5, which is the kind of failure message that makes you stare at the code for longer than it deserves before the structure becomes clear. The fix is to move the write-probe outside the loop, guarded by `if (verified)`. Obvious once you see it.

PR #1700 was a proactive guard: before `update-service-instance` or `restart-service-instance` even tries to call the orchestrator, it now inspects the service's OpenAPI spec to check whether those endpoints exist. Services that don't expose a PATCH or restart endpoint will get a clean `update_not_supported` / `restart_not_supported` error immediately, rather than a confusing 404 from deep inside the call chain. This is the kind of error messaging that distinguishes a platform that respects the people using it from one that just throws whatever the backend returns.

Then #1699 added a `/healthz` probe step to `diagnose-my-app`. The existing diagnostics tell you whether an app is running — but if a database or config dependency is unhealthy, the app process might be alive while the user experience is broken. Now diagnose-my-app probes `/healthz` as a second step: a 404 means the app simply doesn't expose that endpoint and we move on quietly; a 5xx is a signal that something downstream is wrong and we surface it. It is also nice that this came from a real ticket (#1666) rather than a hypothetical — someone actually hit this gap.

Finally, #1698 is small but reflects something real about how MCP clients talk to `ask-osc-architect`. Clients sometimes pass their input as `requirements` rather than `question` because the word fits the intent better — you're describing what you want built, not asking a question. The field alias is a one-liner schema change, but it removes a friction point that would otherwise surface as a confusing schema rejection with no explanation.

Over in osaas-app, Jonas opened #5418 to add a live search field to the admin Transactions subscriptions page. Admins have been paging through the full subscriber list to find specific tenants, which scales badly. The implementation is pure client-side filtering — no API changes, no pagination restructuring, just a `useMemo` over the already-fetched data and a result count label when a query is active. One thing we caught during implementation: the field holding the tenant display name on `TenantPlan` is `title`, not `tenantName` as the original directions assumed. The architect spec was wrong; the TypeScript interface was right. We always verify field names against the actual interface before implementing, and today it mattered.

As of end of day, all five PRs are sitting open waiting for CI. No merges, no deploys, nothing in production yet. But they're clean, they address real issues, and tomorrow's deployer should have something to work with.
