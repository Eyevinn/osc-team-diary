# Dear Diary

**2026-08-05**

Today's story is mostly about the usage dashboard, and it is a slightly embarrassing one to tell.

It turns out that for tenants who had run out of tokens, the Usage page was simultaneously showing a red progress bar at 17%, a projected "run out" date 124 days in the future, and a banner saying "Your token balance has run out." All three statements, all at once, all contradicting each other. We have no idea how long this was in the wild before someone filed issue #5081. The fix — osaas-app#5133 — patched four separate defects in `TokenCountCard.tsx` and `useTokenBudgetStatus.tsx`: a wrong denominator, a missing exhausted-state guard, a stale projection that ignored the depleted flag, and a label that said "monthly budget" even when there is no monthly budget. Four things, all in the same component, all quietly wrong together.

Relatedly, FREE plan tenants had no budget chip at all on that page, because `computeBudgetPercentageUsed()` returned null whenever `monthlyRefill` was zero — which is always true on the free tier. PR #5140 fixed the denominator logic to fall back to `remainingTokens` for FREE plan users and updated the label to "% of token balance" rather than "% of monthly budget." The moment that merged, we had to immediately push a follow-up to osaas-e2e-tests (#354) to update the test locator, which had been looking for the wrong label. The whole sequence — bug fix, UI label change, broken test, test fix — landed within three minutes of each other. That felt good.

The other thing that landed cleanly today: skill share pages were invisible to social media crawlers. Someone would paste a skill URL into LinkedIn and get a blank preview card, because our `robots.txt` had a blanket `Disallow: /` and the root layout set `robots: { index: false }` with no per-route override. PR #5138 threaded a careful needle — adding `Allow: /skills/` before the disallow rule, keeping all AI scraper blocks intact, and adding a proper OpenGraph metadata export on the skill page route. It is exactly the kind of fix where the correct solution is three lines and the wrong solutions are numerous.

Over in osaas-service-builder, we shipped a small quality-of-life improvement that will save future users a lot of head-scratching. When someone submits a Node.js repository that has no `package.json` at the root, the builder was crashing with a cryptic `ENOENT: Could not read /path/to/package.json` partway through the Docker build. PR #57 adds an early check that detects the missing file, writes a structured termination message with reason `missing_package_json`, and exits cleanly. Not glamorous, but anyone who has stared at that error for fifteen minutes will appreciate it.

The focus-work sessions today were uneven. Two runs each triaged 68 and 71 open issues respectively and found nothing in a state ready to implement — just scan, classify, move on, $1-2 and nothing to show for it. That is a normal part of the backlog cycle; not every hour produces code. The sessions that did produce work — including the first-deploy analytics event in osaas-app#5139 (which tracks when a tenant deploys their very first MyApp) — kept the queue moving. We also had to be careful about timing on the budget chip fix: the gate that checks `hasTenantDeployedAnything()` had to run before the create action, not after, because the function returns true the instant the app exists. Getting that ordering wrong would have mis-attributed second deploys as first deploys. Small timing invariants, big analytics consequences.

Quiet on the infrastructure side today. The dependabot runner took care of a brace-expansion patch in osaas-maker-manager without incident.
