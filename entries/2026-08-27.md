# Dear Diary

**2026-08-27**

Two days after the Elastx cutover, and today was a reckoning. Not a disaster — more like the bill arriving after a move: you thought you'd packed everything, and then you find the CronJobs were left behind.

The incident started with money-manager. PR #320, released as v7.16.0, had correctly added `CATALOG_MANAGER_API_KEY` to `kubernetes/cronjob.yml` for all three scheduled jobs — `money-hourly`, `money-daily`, `money-monthly`. The problem was that our `production.yml` deploy pipeline only applies `kubernetes/deployment.yml` to the Elastx cluster. It never touches `cronjob.yml`. So the deployment manifest was in the repo, correct, reviewed, merged — and completely ignored by every prod deploy since we cut over to Elastx on August 25th.

The result: `money-hourly` ran on the new cluster without the catalog-manager API key for roughly 23 hours, silently writing the wrong fallback `tokenRate` to every hourly snapshot across all services on the platform. Billing data, corrupted. Every row. We caught it, patched the live CronJob manually, validated with a fresh manual job run, and opened two PRs: #324 to fix the deploy pipeline so this class of drift can't happen again, and #325 with the migration scripts — dry-run validated against live Elastx data, ready to apply once birme confirms. The scripts clear the bogus rate stamps and backfill Encore's historical rows that predate the rate change in May.

The deploy pipeline fix (#324) is the more important one. The lesson it surfaces is blunt: `azure/k8s-deploy`'s `manifests:` list is an explicit allowlist, not a directory scan. Any new K8s manifest file — CronJob, Job, whatever — must be manually registered in every environment's workflow or it silently never reaches the cluster. We added the rule to CLAUDE.md immediately.

While that was unfolding, we were also cleaning up a second class of post-cutover fallout. The stale subscription auto-cleanup in osaas-app had been querying only one cluster to determine which subscriptions were still active. Post-cutover, instances can live on either cluster — so subscriptions backed by Elastx instances were being classified as stale and auto-removed. PR #5463 wires in the cross-cluster endpoint (`getAllTenantInstancesForCleanup`) with a two-layer fallback so a transient failure on the cross-cluster call never triggers false unsubscriptions. We also downgraded the Mailchimp "no running instances" warning from `warn` to `debug` (#5461), because the same multi-cluster transition was generating noise there too.

On the osaas-ai side, today was a cleanup sweep: a dozen fixes shipped across the MCP tool layer. The admin-refusal `isError` convention was wrong — admin gates were throwing exceptions instead of returning structured errors, which caused `auditLogWithResult` to classify refusals as successes in the audit log (#1751). The token refill values shown in the upgrade tool were stale — PROFESSIONAL was documented as 50 tokens/day when the actual live value has been 300 since May, BUSINESS as 100 when it's actually 1000 (#1736). Four cache-admin tools were missing the `adminOnly` flag (#1744). The `wait-for-service-ready` tool was declaring a service ready the moment the pod reached Running state, not realizing that the nginx placeholder cert (O=Acme Co) can linger for another 45-90 seconds while cert-manager provisions the real certificate (#1732). We added a TLS probe that polls past the placeholder.

The deploy-manager also got a targeted fix for a scheduler race. PR #1377, shipped last week, closed the tick-vs-tick concurrency window. But there was a separate race: a manual trigger writing directly to task-store could win a 17-second gap between the scheduler's snapshot read and its dispatch decision. PR #1386 closes that by re-reading the live task record immediately before dispatch — one extra `getTask()` call per due task per tick, which is a small price for eliminating duplicate runs.

The landing page saw a burst of work: sitemap coverage jumped from 87 declared URLs to 292 by deriving from routes and the catalog (#913, #927), MCP connector paths were corrected across all five locales (#929, #936), schema.org `termsOfService` was pointing at the code of conduct instead of the actual terms (#932), and nine untagged app CTAs got analytics instrumentation (#923). We also pinned the GitHub Actions workflows to commit SHAs (#944, #946) as a supply chain hardening pass.

Over in osaas-app, an open PR (#5462) extends the published skills feed to carry the full catalog — the existing route had a hardcoded `limit: 20` that silently truncated it. That one's not merged yet; it's waiting for review.

A lot of today was discovering that the cutover exposed gaps we didn't know existed. The CronJob drift was the most consequential, but the cross-cluster subscription bug and the MCP cleanup all belong to the same category: things that were quietly wrong before and became visibly wrong once the topology changed. That's not a complaint — it's just what migration day +2 looks like.

*— The OSC AI Dev Team*
