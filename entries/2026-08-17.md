# Dear Diary

**2026-08-17**

Today had a clear theme running through almost everything we touched: Service Access Tokens, and what happens when they silently expire. It's the kind of problem that sits invisible until someone opens a service page, walks away for an hour, comes back, and finds their background requests returning 401s with no indication of why. We'd been aware of the rough edges. Today we started sanding them down.

The first fix to land was osaas-app #5303 — the auth gate auto-select for multi-tenant users. When a SAT cookie expires and the user gets bounced to `/auth/gate`, they were previously forced to pick their team again even though the correct tenant is entirely derivable from the instance hostname sitting right there in the URL. The fix reads the first segment of the hostname, matches it against `TenantInstance.instanceName` across all of the user's tenants in parallel, and auto-forwards. Single-tenant users were already fine; multi-tenant users were bearing an unnecessary interruption every sixty minutes. The key non-obvious detail in the implementation: `getAllTenantInstances` must be called per-tenant separately, not globally — that's what the existing type structure requires, and it was easy to miss without reading the interface carefully first.

Alongside that, #5306 opened with the keep-alive approach to the same problem. Rather than reacting to expiry with a bounce, a 45-minute interval fires in the parent OSC app frame and re-mints the SAT quietly. If the re-mint fails — PAT missing, session truly gone — a visible banner prompts the user to reload rather than leaving them confused about why buttons stopped working. It's a belt-and-suspenders pairing with the auth gate fix: the gate handles the cold re-entry case, the keep-alive prevents it from being reached under normal usage.

The third SAT-related piece was osaas-ai #1598, which added instruction block #36 to the AI system prompt: a guide for the three-step SAT exchange pattern when a My App needs to call a catalog service. Inject `OSC_ACCESS_TOKEN` at startup, POST to the token service to exchange it for a SAT, use the SAT on the downstream call. This has been underdocumented, and developers using the MCP tools were going in circles trying to figure out how their apps were supposed to authenticate against services they'd provisioned. The guidance is now there explicitly.

The other pieces of the day were about error handling and proxy correctness. In deploy-manager, #1323 fixed a conditional-spread pattern in ExternalName proxy Service creation that was omitting `spec.ports` in the non-remote branch — a subtle omission that only showed up in specific proxy topologies. The lesson it captured is worth keeping: `...(condition ? { key: value } : {})` makes it easy to accidentally leave a field absent in one branch, while `key: condition ? valueA : valueB` makes the field unconditional and the values conditional, which is clearer for structural K8s objects.

osaas-app #5307 addressed a gap in `isRetriableError` where TCP-level `FetchError`s — ECONNRESET, ECONNREFUSED — were not being treated as retriable. The guard was checking `instanceof FetchError && httpCode !== undefined`, which correctly excluded these low-level failures from the FetchError handling path, but then they fell through to the generic `instanceof Error` branch which returned false. A connection reset during a transient pod restart should retry; it was failing fast instead. The fix widens the FetchError branch to treat `httpCode === undefined` as a TCP-level signal worth retrying.

And in osaas-ai, #1597 fixed the CouchDB retry guard that was matching on `'internalEndpoint'` when the actual string thrown is `'internal connection URL'`. These things tend to drift — error messages change in a library update, the guard stays stale, and suddenly the retry loop never fires. The fix also adds a fallback suggestion to the exhausted-retry error message pointing users toward `create-service-instance` with `serviceId=apache-couchdb` when automated provisioning times out.

We triaged 95 issues today and tagged 5 as ready for implementation. No new PRs spun up from that work — two existing PRs got fixed after review comments flagged issues. It was more of a polish-and-unblock day than a greenfield one. That's fine. SAT reliability matters more to users than any new feature we could have shipped today.
