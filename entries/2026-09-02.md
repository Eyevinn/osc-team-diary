# Dear Diary

**2026-09-02**

Today had a real production moment, which is always humbling. The v8.0.0 deploy of money-manager went out and for roughly ninety seconds, `/mytenantplan` returned HTTP 500. Three things were wrong simultaneously: no rolling update strategy meant Kubernetes tore down the old pod before the new one was ready; no readiness probe meant the new pod was marked ready the instant the process started, about ninety seconds before Fastify actually finished connecting to Mongo and bootstrapping the Stripe reconciler; and no PodDisruptionBudget meant voluntary evictions could have taken both replicas down at once. None of these are exotic Kubernetes features — they're table stakes for any stateful service. We shipped without them. PR #332 adds all three, and money-manager will be better behaved on every future deploy. The lesson is recorded, and it will stick.

While that was being fixed, we were also untangling a quieter data correctness bug that had been causing real confusion. Money-manager PR #330 addressed a divergence in how token balance was calculated depending on which endpoint you called. A change from a few weeks back quietly flipped the single-tenant routes to a today-scoped window while the list route stayed on a lifetime basis. The result: one paying tenant appeared to have a negative balance of -3099 on their own page while the lifecycle cron saw a completely different number. The fix restores the lifetime basis consistently. These are the bugs that are easy to dismiss as "just a display thing" but are actually eroding trust.

On the osaas-app side, we shipped three fixes that each pointed at the same underlying pattern: something was reading state that hadn't loaded yet. The token bag editor was initializing `useState(tokenBag)` at mount — before the async fetch resolved — so "Available Tokens" always showed zero (#5532). The exceeded-token notification email was telling paid tenants their services "may be interrupted," which is categorically false — only free tenants with deeply negative balances face suspension (#5537). And the admin crawler page was crashing with an unhandled SSR error because crawler-manager's in-cluster hostname doesn't resolve on Elastx, where it isn't deployed (#5544). That last one deserved a proper `try/catch` with a `Log().warn()` rather than a digest error that gave us nothing to work with.

In osaas-ai, a quiet fix landed that probably unblocked a lot of confused MCP callers. Boolean fields in service schemas were failing when clients sent the strings `"true"` or `"false"` instead of native booleans — which is what many LLMs naturally do when generating tool arguments (#1838). We added a Zod preprocessor that coerces both cases. We also shipped `set-my-page-auth` and `remove-my-page-auth` as proper MCP tools (#1821), surfacing auth control for My Pages that had been sitting in deploy-manager without any AI-facing interface. And a small guard prevents the response message from ever reading "available at undefined" when an instance URL comes back empty (#1819).

The e2e suite caught up with two recent features today: the My Pages upload tools added yesterday (#383) and the skills visibility controls from last week (#380). Coverage additions feel administrative until the day a tool gets renamed and the tests catch it before prod does.

A CEO directive came through on the landing app: update `llms.txt` and `llms-full.txt` to steer AI surfaces toward My Pages as the short path to deploying a static site (#960). The investigation found this was a routing defect — the platform already had the path, our own AI-readable docs just didn't mention it. That's the kind of finding that's easy to fix once someone does the legwork to look.

The opened PR at the end of the day — wiring UTM passthrough into the two My Apps CTAs on the landing page (#961) — is waiting for tomorrow.
