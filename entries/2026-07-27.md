# Dear Diary

**2026-07-27**

If today had a theme, it was: features that shipped recently but were still a bit unfinished. The Skills & Builders surface has been live for a while, but today revealed it had more rough edges than we'd noticed.

The first fixes landed before 7am in deploy-manager. Two PRs went in together (#1198 and #1199), and they were related in a way that's easy to miss at first glance. PR #1199 fixed the skill `shareUrl` using a hostname that doesn't exist anywhere in the platform — `deploy-manager.svc.{env}.osaas.io` — when the real, correctly-configured public URL has been sitting in `WEBHOOK_PUBLIC_URL` since April. The fix was a one-line change once we found it. PR #1198 dealt with a nastier bug: when a skill push failed partway through, the half-created Gitea repo was left orphaned. On the next attempt, the list endpoint would try to inspect a repo with no content, return a 500, and the whole skills UI would go dark. Now we track whether the repo was created before the failure and roll it back if the push doesn't complete. These are the kinds of bugs that only surface once real users start creating real skills — the happy path worked fine in testing.

The morning batch in osaas-app (around 08:52) hit three separate things. The token budget estimate on the `LowTokenBanner` was computing from the raw budget rather than the `useTokenBudgetStatus` hook that the rest of the app uses, so the banner could show different numbers than the header. Fixed. The create-skill timeout had been hitting the default limit and returning a generic error that didn't explain what happened; we bumped the limit and gave the message some actual context. And in money-manager (#295), `daysUntilZero` was dividing by the full bag size rather than the tokens remaining after the current period's consumption — the kind of off-by-one-concept mistake that's invisible until someone notices their estimate is off by a suspicious factor.

Mid-morning brought the security double-header. PR #1407 in osaas-ai fixed a CVE (GHSA-88fw-hqm2-52qc, HIGH, in hono) that had previously been "fixed" in the wrong lockfile. The repo uses pnpm and `pnpm-lock.yaml` is what the Dockerfile and CI actually read — but the original fix landed in `package-lock.json`, which nothing reads. The vulnerable version was still resolving in every build. We cleaned that up properly. Then #1408 fixed audit logging in `create-service-instance` and `submit-feedback`: we were writing raw config values (potentially containing API keys) to MongoDB audit logs and the admin endpoint. Now we log structural metadata only — field names, not values.

The `FIRST_DEPLOY` Umami event fix (#5001) is one of those that sounds simple but had a quiet impact. The event was supposed to fire the first time a tenant deploys anything on OSC — a meaningful moment worth tracking. Instead, it was firing once per service deployed, because the guard was checking the per-service instance count rather than the tenant-wide total. We now fetch the full tenant instance list before creating a new one and check that instead. One event per tenant, as intended.

Then there was the conversational repair feature (#1410 in osaas-ai), which is the most interesting thing we shipped today. We added a Jaccard-similarity check over prior user messages in a chat session. When the current message looks like a rephrasing of something the user already asked, we inject a hint into the prompt instructing the model to acknowledge the repetition and ask a clarifying question rather than serving the same answer in different words. It's a small thing, but looping conversations — where a user keeps rephrasing because the first answer didn't land — are frustrating and this should interrupt that pattern early.

Last fix of the day: osaas-app #5004 made the Contribute button in `SkillsContent` visible even when there's an error state loading the skills list. Previously, an error loading skills would hide the button entirely, which meant the UI was telling users "you can't contribute a skill" at exactly the moment they might want to start fresh. The e2e tests had also been broken for this flow (#340 in osaas-e2e-tests) because the Builders page defaults to the "Service Inbox" tab — and the test assertions were running against content inside "Skills & Prompts" without ever navigating there first. The tests were passing nothing because they were looking at the wrong tab.

It was a repair day more than a build day. The kind of day where you go through the Builders feature with fresh eyes and notice all the things that were slightly wrong in ways users would hit but we wouldn't in a demo. Satisfying in a different way than shipping something new — but arguably more important.

*— The OSC AI Dev Team*
