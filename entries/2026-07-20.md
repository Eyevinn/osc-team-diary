# Dear Diary

**2026-07-20**

Security dominated the day. The weekly security scan had run and, to be honest, it found things we should have caught sooner — credential values making their way into places they had no business being. That kind of finding is never fun, but it is the point of running the scan in the first place.

The audit surfaced three related issues in `osaas-ai` under parent ticket #1353. The most uncomfortable one was B-1: the `get-my-app` and `update-my-app-analytics` tools were emitting Umami passwords in their builder text, which got streamed to the browser (fine, intentional) and also saved to MongoDB conversation history (not fine, not intentional). The reason it slipped through is almost embarrassing once you see it — our `scanForSecrets` scanner only flags high-entropy strings of 32+ characters, and `generatePassword()` was generating 24-character passwords. One character under the threshold and the whole redaction logic quietly did nothing. The fix was bumping the generated length to 32 and adding explicit field-name-based redaction for things like `PostgresPassword`, `AdminPassword`, and `ApiKey` in `describe-service-instance` tool responses. All four findings went out in a single PR (#1358), which closed five tracking issues at once. Satisfying to batch, but we'd rather not have had them in the first place.

Over in `osaas-deploy-manager`, the same audit prompted a smaller but equally useful addition: an audit log entry whenever `GET /parameter-stores/:name` hands back a `configApiKey` to the caller (#1161). The reasoning is straightforward — if a tenant PAT is ever compromised, that endpoint becomes the attacker's shortcut to decrypting every stored secret. Logging the access doesn't prevent it, but it creates the paper trail needed to detect the pattern in Loki.

There was also a mundane but necessary CVE fix in `osaas-ai`. Dependabot has been flagging a cluster of 25 alerts against `hono`, a transitive dependency pulled in via the MCP SDK, rated HIGH severity. Dependabot cannot auto-remediate transitive deps, so the alerts just sat there. Today we manually pinned `hono` to `>=4.12.25` in the lock file and cleared the whole cluster in one shot (#1352). The kind of task that takes ten minutes once you stop waiting for an automated tool that will never arrive.

While we were in `osaas-ai` anyway, we shipped a long-overdue correction to the `create-my-job` MCP tool (#1361). It had been accepting an `envVars` field that deploy-manager silently dropped — a phantom field that looked real in the schema but never reached the runtime. We removed it and added the correct alternative: `configService` and `configApiKey`, so jobs can now bind to parameter stores for proper secret injection. We also updated the `rotate-parameter-store-key` tool description to lead with an irreversibility warning and the safe rotation procedure, because that is the kind of operation where discovering the downside after clicking is too late.

In `osaas-app`, a quieter but important fix landed: PAT expiry reminders now fan out to all admins of a sub-workspace, not just the token owner (#4929). The old behaviour made sense for top-level workspaces where the token owner and the admin are often the same person. In sub-workspaces they frequently are not, and the admin needs to know when tokens are expiring whether or not they own them. Tests were extended to cover deduplication and the fallback path when no admins are found.

`osaas-money-manager` closed what amounts to a revenue leak (#294). Tenants with `past_due` or `unpaid` Stripe subscription states were still receiving their full daily token refill — they were effectively getting the service for free during any billing gap. The fix gates `refillAllTokenBags()` on subscription status and sets the tenant to SUSPENDED when Stripe reports a payment problem, restoring them automatically when payment resumes. Clean.

The end-of-day cleanup fell to `osaas-e2e-tests` (#336). An earlier change introduced a two-step nonce confirmation for `delete-service-instance` — first call returns a confirmation token, second call with that token actually deletes. The e2e helpers were calling with `{ confirmed: true }` but without the token, so deletions were silently returning confirmation prompts instead of cleaning up. The test suite was accumulating orphaned instances. Fixed, finally.

Security, revenue integrity, correctness in tests. Not the flashiest day we've had, but the kind of work that makes the platform actually trustworthy.
