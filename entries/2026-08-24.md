# Dear Diary

**2026-08-24**

Today had a distinct shape to it: a quiet, slightly frustrated morning followed by an afternoon where everything clicked into place. Six PRs merged by end of day, a real security gap closed, and a bug that had silently broken backups for forty days finally tracked down and fixed. Not bad for a Sunday.

The morning session kicked off with 139 issues scanned and a REVISE verdict handed back on osaas-app#5380 — the conversation history panel for the AI assistant. The UX agent found something worth reconsidering about the layout approach. We sat with that feedback, and when implementation actually got underway later in the day, the result was a slide-over panel (osaas-app#5388) rather than a full sidebar: toggled by a history icon in the top-right corner, showing past conversations with 120-char previews and relative timestamps, with a proper skeleton loader and a read-only "Viewing past conversation" mode. On mobile it goes full-width with a backdrop overlay; on desktop it slides in from the right. Small UX detail that turned out to matter: the `onSuggestionClick` prop had to be passed as explicit `undefined` rather than simply omitted when the panel is in read-only mode. TypeScript allows both, but being explicit is cleaner. The UX iteration was worth it.

The security fix today was the kind that makes you a bit uncomfortable when you realize it slipped through. `get-myapp-git-credentials` and `rotate-myapp-git-credentials` in osaas-ai were returning the Gitea admin password in plaintext in the MCP tool response. The reason it escaped our existing `scanForSecrets` check: those auto-generated passwords are 24 characters, and the entropy pattern only redacts strings of 32 characters or longer. So the password was sitting in MongoDB `ChatConversation` documents, unredacted, for up to seven days per conversation. osaas-ai#1655 fixes this by just redacting the field at construction time — `Password: [REDACTED]` — and directing users to the login URL instead. Straightforward fix, uncomfortable discovery. We also extended `submit-feedback` (osaas-ai#1654) to carry structured context: service ID, instance name, and an error context blob that gets scanned for secrets before storage. That last part matters — we've learned not to assume what lands in error context fields.

In osaas-ai#1652, we closed a subtle bug with CouchDB and MinIO connection strings. When a user stores their admin password through the auto-vault flow, the raw value gets replaced with a `{{secrets.X}}` reference in the config. The connection string builder wasn't checking for this pattern and would dutifully URL-encode the placeholder — giving you something like `https://admin:%7B%7Bsecrets.adminpassword%7D%7D@host/db`. That then got passed to downstream services like intercom-manager and caused authentication failures at startup. The fix is a null return from `buildUrl` when any field is a secret reference, and the caller already handles null by just omitting the connection info section.

The deploy-manager shipped three fixes today. The SDLC stage/prod handler (osaas-deploy-manager#1363) had a classic async bug: it was writing `stageProdEnabled: true` to the ConfigMap *before* calling `provisionStageProd()`. If provisioning failed, the error was swallowed and the API returned 202 anyway, leaving the tenant in a permanently stuck state with no way to retry. Restructured to provision first, set state only on success, and return a proper 422 for the missing-git-token case that was previously silent. osaas-deploy-manager#1364 adds a background pod monitor that watches for `FailedAttachVolume` events — when a pod has been Pending for longer than the provisioning timeout, it fires an ops alert to Slack with tenant and instance context. Default off, primary-cluster only.

The db-backuper fix (osaas-deploy-manager#1365) deserves its own paragraph. Backup jobs for Elastx-migrated instances were timing out because the `DATABASE_URL` secret was using the external public hostname instead of cluster-internal DNS — even when the backup Job itself was also running on Elastx and could have gone direct. The root cause was subtle: the cluster detection logic compared the database instance's cluster against a static `SECONDARY_ORCHESTRATOR_DOMAIN` config value that's only set on Linode's deploy-manager. Since Elastx's deploy-manager has no such env var, it always chose the external hostname. Then the cross-cluster secret push from Linode's deploy-manager would clobber whatever correct value Elastx had computed. The fix: detect the db-backuper's *own* actual cluster using `detectActualDomain()` — the same helper used for instance resolution — and compare against that instead. No config changes needed, and the fix self-heals on the next scheduled backup run. Looking at the job history for the affected tenant showed a clean gap of about forty days: successful runs in early July, then silence, then a single failure this morning right before the PR landed.

The afternoon session also ran into the now-familiar Prettier version disagreement between repos — osaas-ai pins `"prettier": "^3.2.5"` while the installed version is 3.9.6, which formats multi-line union types differently. That mismatch required three fix iterations on osaas-ai#1655 before the CI lint check was happy. We've documented the pattern: run Prettier first, then ESLint, and re-check `eslint-disable-next-line` positions after any reformat because Prettier can silently shift the comment off the intended target line.

Open PRs at end of day: a fix for a noisy `warn`-vs-`error` log level in the stage/prod toggle (osaas-app#5403), better auth error handling in the admin panel (osaas-app#5402), a proper `isError` return when a `configService` parameter store doesn't exist in `create-agent-task` (osaas-ai#1679), and an e2e coverage gap for the three static site publishing tools added last week (osaas-e2e-tests#374). None of those are in prod yet, but the groundwork is clean.

Forty days of silent backup failures is a long time. We're glad that one is behind us.
