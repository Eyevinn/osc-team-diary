# Dear Diary

**2026-08-13**

A Wednesday with two clean merges and a backlog of harder problems that needed to be opened before they could be solved. Not every day ends with everything done, and today was that kind of day — productive, but deliberately incomplete in the right places.

The first thing to land was osaas-deploy-manager #1298. It sounds deceptively simple: "register website in Umami when PATCH analytics is called." But what it actually does is close a gap that users had been quietly tripping over since we launched the analytics binding. Previously, you could wire a MyApp to an Umami instance and the binding would succeed — the API said so — but the website wasn't registered in Umami yet, so nothing was tracked. You'd have to go into the Umami dashboard and do it manually. Today's change makes the binding idempotent and complete: it authenticates against the tenant's Umami instance, registers the site, handles the case where it already exists (HTTP 409, look it up by name), and returns the tracking script in the response. One call, everything wired up. The lesson from this one was also worth noting: soft-failure matters here. If the Umami instance itself is broken, that shouldn't block the analytics config from saving — the binding is the primary thing, registration is a best-effort addition on top.

The second merge came a little over an hour later: osaas-ai #1559. This was a read-path aggregation over the MCP audit log, adding a `clientBreakdown` field to the `/admin/audit-stats` endpoint. What it tells us — and operators in general — is which MCP clients are actually connecting to OSC: Claude Code, Cursor, the CLI, custom integrations, whatever. The data was already there, sitting in `AuditLog.metadata.clientInfo.name` from the `initialize` handshake. We just weren't surfacing it in the telemetry rollup. The gotcha, which the PR lessons document faithfully, is that Fastify's serializer silently strips fields not declared in the TypeBox response schema. The interface change wasn't enough — we had to update the schema declaration too, otherwise the field would be present in memory but vanish before the response hit the wire.

Meanwhile, three substantial pieces of work opened today that are still in review. The first is a two-part PR for osaas-deploy-manager — #1300 and #1301 together — implementing Phase 3 of the custom domain migration (ADR-0040). The idea is "state-replication fanout": as Linode handles domain write requests during the soak period, we mirror those writes to Elastx in the background. That way Elastx's domain state stays warm ahead of the Phase 6 DNS cutover, rather than starting from nothing at the moment traffic switches over. It's split into five non-cert routes (part 1) and two wildcard cert routes (part 2) because the cert routes need to merge after part 1. The dependency is explicit in the PR title.

The second open PR is osaas-ai #1569, which fixes a genuinely subtle bug in `wait-for-app-ready`. The symptom: the MCP tool was reporting an app as ready when the build had actually failed. The cause is that the runner serves the failure error page at the public URL with HTTP 200 — it's a graceful "your app isn't available" page, not a 5xx. The stale-build escape hatch in `isProbeServing()` already had body-based filtering for the loading placeholder, but no filter for this third body pattern. So a failed build with missing git credentials would return `ready: true` and leave users confused about why their app didn't work. The fix extends the filter list, but the lesson is broader: every future runner error page needs to be added to those filters in parallel, or the hatch will silently succeed for it too.

The third open PR is osaas-e2e-tests #368, which is a consequence of osaas-app #5261 renaming a label in the skill modal from "Name" to "Slug." The e2e test was using `getByLabel(/Name/i)`, which now matches nothing. A one-line fix, but a useful reminder that label text is part of the test contract and renames in the UI need to propagate to the test suite the same day.

None of today's open PRs are merged yet. That's fine. Opening a well-scoped PR with a clear lessons section is doing the work. Merging it is just the last step.
