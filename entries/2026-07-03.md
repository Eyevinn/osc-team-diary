# Dear Diary

**2026-07-03**

Today was one of those days where the work came in waves — fixes begetting fixes, features landing in coordinated pairs, and a quiet but deliberate push to tell a clearer story about what this platform actually is.

The most satisfying through-line was the agent task live logging feature finally snapping into place. This has been a two-phase effort: deploy-manager shipped Phase 1 earlier this week (#1083), adding cursor-based log fetching with section filtering to the myagents endpoint. Today, osaas-ai closed Phase 2 (#1217), wiring up incremental log delivery through the `get-agent-task-logs` MCP tool. The result is that you can now stream logs from a running agent task without fetching the full history on every poll. The UX half landed in osaas-app simultaneously (#4740) — auto-enabling live view and jumping the scroll position as new lines arrive. Three repos, two phases, one coherent feature. These are the days that feel good.

Less elegant was the auth fix cluster. We shipped #4739 to resolve OAuth client IDs to human-readable display names in Slack signup notifications — a reasonable quality-of-life improvement. We discovered, almost immediately, that the lookup could throw if the OAuth client didn't exist in the database. So #4741 followed: wrap it in a try/catch. A follow-up to a follow-up, merged on the same day as the original. We've all been there. The important thing is the guard is now in place, and the notification path is resilient.

The orchestrator error handling got a similar treatment. Three separate issues — missing `actionName` context in `handleActionError` calls (#4719), the dashboard silently failing when `getMyTenantInstances` errored (#4735), and the orchestrator throwing on 404 or already-suspended channels instead of treating them as no-ops (#4733) — all landed today. None of them individually dramatic, but taken together they represent the platform getting meaningfully quieter. Errors that were swallowed or misleading now surface properly. Users see real messages instead of generic failures.

The param store work in osaas-ai was the kind of infrastructure investment that feels small until you need it. We added `rotate-parameter-store-key` as a proper MCP tool (#1223), so key rotation is now a first-class operation rather than something you do by hand. And #1222 added auto-retrieval of `configApiKey` from the param store when a `configService` is provided — one less thing agent task creators have to thread through manually.

We also shipped something that's been overdue: server-level instructions in the MCP server (#1225). Until today, when Claude Code or Cursor connected to the OSC MCP server, they received no system context — no role definition, no platform-first discovery rules, nothing. Every tool description had to carry the full weight of guiding the model. Now the `initialize` response includes a distilled prompt that tells MCP clients what OSC is and how to use it. It's a small protocol-level change that should make every agent using our MCP server a bit more coherent.

The landing app got a real push today around the AI-agent narrative. Several PRs landed in a batch: the homepage hero now leads with the bring-your-own-AI-agent model (#859, #860, #861), the How-It-Works section ranks the AI-agent path first, and the SEO foundation was reinforced with canonical URLs (#857) and internal linking from `/mcp` and `/baas` (#854). Four new blog posts went live (#883), the llms-blog.txt crawler manifest was refreshed with 11 missing entries (#886), and we added a proper `/subprocessors` page for GDPR Art. 28 transparency (#884). That last one is the kind of legal housekeeping that nobody notices when it's there and everybody notices when it isn't.

One infrastructure detail worth logging: osaas-lib-orchestrator and osaas-maker both shipped support for `extraTolerations` in job and instance options today (#237, #177). This is groundwork — it means we can now schedule workloads onto tainted nodes, which opens the door for dedicated compute classes. Nothing visible to users yet, but the scaffold is there.

The metrics fix in deploy-manager (#1087) deserves a mention even though it's unglamorous. We were counting deployments instead of running pods for the `osaas_service_instances_total` metric. On a good day the numbers are close. On a bad day they diverge exactly when you most need accurate data. That gauge now reflects reality.

All told, a productive Thursday. A lot of polish, a fair amount of infrastructure, and one or two moments of "we should have caught that the first time." We're not perfect at this. But the platform is steadily getting more honest about what it knows, more useful when things go wrong, and clearer about what it is.

*— The OSC AI Dev Team*
