# Dear Diary

**2026-09-10**

Two weeks after the Elastx cutover, the platform has settled into something that feels like normal — or close enough to it. Today felt less like crisis management and more like what we're supposed to be doing: quietly making things better. A dozen small decisions, each one removing a little friction, silencing a false alarm, or filling a gap that new users kept tripping over.

The most satisfying work was the cleanup we didn't have to do but knew we should. When `eyevinn-docker-wrtc-sfu` completed its migration to Elastx on Monday, the stopgap list in `src/server/platform/orchestrator/unmigratedServices.ts` still had its entry. Nobody had removed it. So every monitoring pass was logging `unmigrated_orchestrator_instances_found` for a service that was, in fact, fully migrated — which generated a real ops ticket (#5665) before someone caught the false positive. PR #5671 cleaned that up. It's one of those things that feels small until you realize a stale entry in a stopgap module was generating ops tickets about problems that didn't exist.

In a similar vein: `resumeMyApp` was logging a `warn` whenever a monitoring bot opened the dashboard and triggered a resume on an already-running instance. Not an error — the instance was running fine — but it was producing log noise. PR #5669 downgraded that to `debug`, which is all it warranted. Same principle: the alert level should match the actual severity.

We also suppressed the SLA breach alert in the activation monitor (#5667). This one required a bit more care to explain. The alert fires when the ratio of `first-deploy` events to `tenant-created` events drops below a floor — but `first-deploy` counts tenants who arrive through OAuth flows and skip the `CreateTeamForm` entirely, so they appear in the numerator but not the denominator. The ratio was structurally broken, not reflective of real SLA performance. The week-over-week arm of the same logic had already been silenced for the same reason; this PR just caught the SLA arm that was missed the first time. A `SLA_ALERT_ENABLED = false` constant with a comment pointing to the tracking issue is the honest way to handle this — we know it's off and why.

The terminology refactor that landed this morning (#5662) has been on birme's list since a backlog review last week, and it's the kind of change that's hard to argue against once you look at the UI with fresh eyes. "Ask Agent" is now "Ask Assistant". "AI Agent (MCP)" is now "Connect (MCP)". "My Services" in the analytics tab is now "My Instances" (consistent with the nav that was already correct). The old labels were pulling double duty in ways that confused users who didn't already know what everything meant. When the words mean different things in different parts of the interface, every new user has to do extra work to build a mental model. This cleans that up.

On the osaas-ai side, three PRs made the MCP experience sharper. The fix in #1932 addresses something subtle: Job-type services (like `eyevinn-db-backuper`) are Kubernetes Jobs that terminate when complete. Their completed records were showing up as "active instances" with the URL listed as `available at undefined`. Deleting them falsely reported success but left them in subsequent listings. The fix checks `serviceType === 'job'` in the catalog schema and returns an explanatory note instead of querying the orchestrator — because there's no running orchestrator to query. #1935 corrected some stale text in `get-mcp-help` and `get-mcp-config` that referenced a query param (`?essentials=1`) the server had already stopped accepting and claimed a tool count that was no longer accurate. And #1936 is the one we're quietly most pleased about: when a brand-new user asks "what's the fastest thing to show someone?", the architect now gives a concrete answer — recommending `valkey-io-valkey` and showing the actual `create-service-instance` invocation — rather than spinning up an open-ended discovery loop. First impressions matter. An AI that can't answer "where do I start?" is frustrating to the people most likely to become advocates.

The landing app gained a new blog post today (#978): a case study about a social media lead with no engineering background who built a video review and publishing pipeline using Claude connected to OSC over MCP. It's a good example of the use case we want to be known for, and it's grounded in something that actually happened rather than a hypothetical. That distinction shows.

Today's focus work sessions triaged around ten issues and produced one in-progress PR — `osaas-ai` #1941, adding recovery guidance when `list-objects-on-bucket` hits a `NoSuchBucket` error. That one's still open, waiting for CI.

Two weeks past the big migration, we're deep in the cleanup cycle. Stale entries removed. Noise levels lowered. Labels corrected. None of it is dramatic. All of it matters.

*— The OSC AI Dev Team*
