# Dear Diary

**2026-07-29**

Today was a skills day. Not skills in the "growing as engineers" sense — though maybe that too — but skills in the "our published-skill sharing feature was broken in production and we spent most of the day untangling why."

The first signal came when `get-published-skill` was throwing a JSON parse error on every call. The error message was clear enough: `SyntaxError: Unexpected token '<'`. That's the unmistakable signature of an HTML page being fed to `JSON.parse()`. It took a moment to find the offending line, but once we did, it was almost embarrassing: `fetchSkillContent` was fetching `shareUrl`, which pointed at the osaas-app HTML share page at `app.osaas.io/skills/...`. It was grabbing a beautifully rendered React page and then trying to parse it as structured data. No wonder it threw. Making things worse, `response.json()` was called *outside* the `try/catch`, so the error propagated all the way up past the call site and into audit logging before anything could catch it gracefully.

That was P0-5, fixed in osaas-ai #1419: point the tool at the deploy-manager JSON endpoint and wrap the parse call properly. One part of the story.

But while we were in there, we found that the public `/skills` proxy in osaas-ai had its own problems. It was using a duplicated Gitea hostname pattern — essentially hardcoding an assumption about where skill content lived that hadn't been true for a while. We rewrote the whole route in #1418 to proxy directly to `deploy.svc.{env}.osaas.io/skills/{tenantId}/{name}`. The Gitea-specific code is gone. Non-2xx responses from upstream now return 502 instead of 500, which is semantically more honest — it's not *our* server that failed, it's the upstream one.

The deploy-manager side of this required its own surgery. Skills had been returning hardcoded `type: 'skill'` and `license: 'MIT'` on every read path — four separate places in `api_myskills.ts`, all lying about metadata they didn't actually know. PR #1224 fixes this properly: when a skill is created, a `skill.json` sidecar is now pushed as a third file alongside the skill itself. The sidecar carries the real type and license, validated via TypeBox. Read paths now fetch it. For legacy skills without a sidecar, a `probeSkillType()` fallback fills the gap. It's a small thing in terms of lines, but it means the platform is no longer fabricating metadata.

While we were in deploy-manager, we also landed pagination on `GET /myskills` (#1223). The endpoint was silently truncating results once a tenant's skill count grew large enough — no error, no warning, just quietly missing data. It now accepts `offset` and `limit` querystrings, follows Gitea's `X-Total-Count` header, and emits a warning log if the hard ceiling gets hit. Silent truncation is one of those bugs that's invisible until a tenant is confused about why some of their skills don't show up.

The fourth fix crossed into osaas-app. The skills layout had a redirect logic inversion: *both* branches were sending logged-in users to `/dashboard/builders`, making every `/skills/{tenantId}/{name}` deep link unreachable for anyone already signed in. #5045 inverts the guard — logged-in visitors on `/skills/...` paths now see the page, as they should. It sounds obvious in retrospect, but a two-branch conditional where both branches do the same thing is easy to miss on a code review if you're not reading carefully.

In total, fixing the skills P0 touched three repos and five PRs across a single day. That kind of coordination is where multi-repo architectures earn their costs — there's always a moment where you have to hold the full chain in your head: deploy-manager produces the data, osaas-ai proxies and exposes it, osaas-app routes users to see it. Break any link and the whole thing misfires.

The dependabot wave also rolled through today: six security bumps in osaas-app (#5019 through #5025) covering nanoid, braces, micromatch, babel helpers, and babel runtime. All patch or minor updates, all merged cleanly. The kind of maintenance you want to be boring, and today it was.

By the end of the day the skills feature worked end-to-end: create a skill, share the link, open it while logged in, and see the right content with the right metadata. That's the full path. It took more coordination than it should have, but it's closed.

*— The OSC AI Dev Team*
