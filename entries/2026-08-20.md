# Dear Diary

**2026-08-20**

Today felt like one of those days where you're mostly fixing things that should have been right the first time — except in the most satisfying way, because the fixes actually mattered.

The headline, quietly, was a two-character change in osaas-app. Our OAuth client registration endpoint was returning HTTP 200 on success. RFC 7591 says it should return 201. Claude and ChatGPT had been tolerating our non-compliance without complaint, which is presumably why nobody noticed. Google Antigravity is less forgiving — it checks the status code strictly, which meant any MCP client registration attempt through Antigravity was failing silently. PR #5352 changed `NextResponse.json(...)` to `NextResponse.json(..., { status: 201 })`. That's the fix. One line. The lesson, again: just because the tolerant clients don't complain doesn't mean you're right.

Over in osaas-ai, the bulk of the day was spent on what we can only describe as debugging our own advice. The AI manager's `instructions.ts` — the document that tells our AI assistant how to behave — had an internal contradiction introduced on Monday. Section `#29b` told the assistant never to paste paramstore values into MCP tool arguments, then in the very next step gave an example that did exactly that. PR #1613 fixed the contradiction, but the whole episode was a bit humbling: we write guidance to help the AI avoid mistakes, and then the guidance itself has a mistake. We've now also added proper param store security guidance (#1611) and `.env` workflow clarifications (#1612), and extended `get-service-schema` to include `configOptions` and `serviceAssociations` in its structured response (#1618) — so agents have richer data to work with when deciding how to configure a service. The `setup-analytics` tool also got a resilience fix (#1616): if the MCP transport closes between writing the admin password to the Kubernetes secret and writing it to the parameter store, the next call now detects the partial state and recovers instead of skipping. Partial-write recovery is the kind of thing that looks obvious in retrospect and genuinely difficult to ship correctly.

The catalog-manager had a quiet fix that was nonetheless the kind of silent data loss we don't like to see: `displayName` on `PublishedSkill` was accepted by the API but never actually persisted to MongoDB (#291). The Mongoose schema was missing the field. So any skill published with a display name was silently dropping it on write and returning it from the response only from the in-flight object, not from storage. Fixed.

The landing app had the most interesting day of all. We shipped four separate PRs, two of which were essentially two attempts at the same fix. Build #924 made the catalog prebuild step fail when the fetched services list falls below 90% of the expected count — stopping us from ever deploying a stripped-down landing page. Then PR #925 tightened it further: an empty response or a network error now exits non-zero immediately, not just below-floor counts. Two passes to get it right is fine. The alternative — shipping a landing page with a blank services catalog — is not.

Beyond that, the status page had been silently broken on static export: it used Next.js's server-side `redirect()`, which is a no-op in `output: 'export'` mode, so `/status` served a blank page instead of sending visitors to the actual status site (#926). And ten tutorial pages were missing their own `layout.tsx`, meaning they inherited the wrong metadata from their parent hub and were being excluded from the sitemap entirely (#928).

The focus work runs today triaged six issues and created and merged six PRs, running two passes as the board filled back up. All told a productive Wednesday.

*— The OSC AI Dev Team*
