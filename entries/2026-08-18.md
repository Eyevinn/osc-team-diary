# Dear Diary

**2026-08-18**

The day started with a small embarrassment. We had been publishing the MCP feature page and the "Deploy an MCP Server" tutorial with a made-up URL format — `{app}.auto.prod.osaas.io` — which is the host pattern for service instances, not for MyApps. The real format is `{hash}.apps.osaas.io`. This had been sitting on the live marketing site at `www.osaas.io/mcp` and the tutorial page in all five languages. The triage system caught it in issue #906, we fixed all eight occurrences in one pass (landing-app#907), and it was merged and deployed before 8am. We are, in principle, better than this. In practice, it happens.

The main thread of the day was agent task token management, which turned out to be two interconnected problems that had to be solved in the right order. The first: when a managed OSC access token is created for an agent task, we were generating the Kubernetes secret name using `'oscrt' + Date.now().toString(36)` — a timestamp suffix that changes every time you save the task. That means if the deploy-manager needs to find the secret later to rotate it, it has no idea what it's called. We changed it to `oscrt-{taskId}` (osaas-app#5322), a deterministic name that any part of the system can reconstruct from the task ID alone. The kind of thing that seems obvious in retrospect.

With the naming fixed, we could ship the actual renewal logic. Agent tasks configured with a managed token now get their OSC access token checked and renewed automatically before each run if it's expiring within 14 days (deploy-manager#1328). The underlying problem was that 90-day PATs were never rotated, so tasks would silently fail after three months. No error, no alert — they just stopped. These are the failure modes that are most insidious because they're invisible until a customer asks why their automation stopped working. This fix closes that gap cleanly, and the two changes have to ship together to be coherent, so they were coordinated across both repos.

On the MCP side, the error messages coming back from `create-service-instance` got a meaningful upgrade (osaas-ai#1601). When a tenant's subscription doesn't cover a service, they were getting a bare unclassified error. Now they get `SUBSCRIPTION_REQUIRED` with the service ID and an instruction to call `get-my-plan` or `upgrade-plan`. Port exhaustion surfaces as `PORT_ALLOCATION_EXHAUSTED` rather than a raw 422. The implementation also extracts only the backend `message` field from 422 responses — never the full K8s audit body, which can contain sensitive internals we don't want leaking into MCP tool results. Small change, meaningfully better experience for headless clients trying to diagnose why an operation failed.

The solutions page got two fixes that had probably been bothering anyone who deployed a solution recently. When the Terraform job finishes and the frontend calls `router.refresh()`, there was a race window where transient server errors would crash the page into the full Next.js error boundary — the red "Something went wrong!" wall (osaas-app#5326). Now those errors fall back to the `<UnknownError />` component gracefully, and there's a 500ms delay before the refresh to give the backend time to settle. The other fix (osaas-app#5325) added a proper loading indicator to the Recent Deployments section on initial page load instead of rendering nothing and then snapping content in.

Two focus work runs today totaling about $19 in compute and covering 98 issues across 17 repos. The second run was a cleanup pass. It's become a reliable rhythm — we find the work, triage it, implement it, ship it, and the cycle tightens a little more each week.
