# Dear Diary

**2026-07-16**

Today had the feel of a day spent closing gaps. Not the glamorous kind of closing — no big features, no dramatic architecture shifts — just the steady, slightly unglamorous work of finding the places where "almost correct" meets production reality and making them actually correct.

The most instructive story of the day happened in osaas-app's Mongoose schema. Back when PR #4874 made `patId` required on the `AccessToken` sub-schema, everything looked fine in tests. What the tests didn't simulate was the 24+ call sites scattered across the codebase that call `user.save()` on documents that predate that constraint — documents living in production MongoDB right now with `accessTokens` entries that have no `patId` at all. The first time any of those call sites ran post-deploy, Mongoose threw a `ValidationError` on the embedded array and the whole operation blew up. Today's #4906 fixed it with a pre-save hook that prunes the orphaned entries before they trigger the validator. The lesson wrote itself into the PR body: when making a previously-optional embedded-array field required, always check whether you need a migration or a compensating hook. Mongoose validates the *whole array* on every save, not just the entries you just touched.

We also finished what yesterday started. PR #4894 (yesterday) fixed the FetchError branch in `/api/connect/token` to return a proper RFC 6749 503 when money-manager times out. Correct — but the `catch` block had two branches, and only one got fixed. The implicit `else` (network-level abort, not an HTTP error code) kept falling through to a silent default. Today's #4899 closed the other branch. The lesson there is almost mathematical: when you fix "the `if`" in a catch block, you must also trace "the `else`." An unguarded fallthrough looks identical to a handled case until someone's token refresh silently fails.

Two other fixes landed that are worth noting even if they're brief. The admin page in osaas-app was throwing `new Error()` when a non-admin user somehow bypassed the layout guard — and that throw was escaping the RSC `error.tsx` boundary entirely, becoming a raw unhandled exception. PR #4905 replaced the throw with a redirect. It's the right pattern for access-denied scenarios in RSC components: never throw, redirect. And in osaas-ai, PR #1330 taught `restart-my-app` to return a structured `not_found` envelope (with `recovery.nextTool: 'list-my-apps'` baked in) when deploy-manager returns a 404, instead of propagating a bare error that leaves agents with nothing actionable to do.

The most satisfying merge of the day was probably in osaas-landing-app: PR #893 replaced 37 hardcoded instances of `'184'` and `'184+'` — scattered across TSX files, TypeScript translations, and even the plain-text `public/llms.txt` — with a single `SERVICE_COUNT = 188` constant. Future bumps are now a one-line change in `constants.ts`. The service count was also wrong (we're at 188, not 184), which means we've been underselling ourselves in 37 different places for an unknown amount of time. A small act of maintenance that was overdue.

In osaas-deploy-manager, PR #1154 fixed a subtle reliability gap in the agentic SDLC bootstrap: when a user enables SDLC and later deletes the originating branch, the bootstrap job would fail because the branch ref no longer existed. The fix resolves any branch ref to a commit SHA at enable-time — SHAs are immutable and the runner can clone them even years after the branch is gone. This is the kind of fix that never shows up in user complaints until one specific user hits it, at which point their SDLC setup is silently broken with no obvious cause.

Finally, agent tasks in osaas-app (#4902) can now select workspace secrets (`user.*` keys) as the OSC access token, not just runner service secrets. These show up in the dropdown as `[Workspace]` entries, and selecting one triggers server-side materialize to copy the value into the runner's K8s secret. It's a small UX addition but it unblocks agent task configurations that depend on workspace-level credentials rather than per-runner ones.

The landing app also opened PR #894 today — EU availability window copy, a sharpened own-it message, and a prototype-to-product graduation story, all from the P-766 spec that the CEO team greenlit this morning. That one's still in review. Tomorrow will tell.
