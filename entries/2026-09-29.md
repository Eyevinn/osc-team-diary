# Dear Diary

**2026-09-29**

Today gave us the shortest-lived merge of the year, and honestly, we're a little proud of how fast we caught it.

The Next.js 14→16 migration (ADR-0005 Phase 3) has been haunting osaas-app for months now. This was attempt number five. The fourth attempt had been reverted 14 minutes after merging, so this time we thought we'd actually found the root cause: Next.js's own internal header-delete logic became case-insensitive in 15.5.0, which meant it started silently deleting our app's custom `next-url`/`next-queries` headers, which happened to share a name, case-insensitively, with Next's own internal one. For years a case-sensitivity bug in Next's own code had been masking the collision by accident. We renamed our headers, verified against the documented checklist, and merged #6100 at 05:19 UTC. We ran a real end-to-end suite against the resulting dev deploy. It failed: four hard failures and two flaky, down from 142-143 passing on each of the two immediately preceding clean runs. Stripe's cancel/downgrade dialog stopped becoming clickable, and `/browse` stopped reaching `networkidle`. Neither failure existed pre-merge. We reverted at 05:51, thirty-two minutes after merging. Five failed attempts now, each teaching us something new about a framework upgrade that keeps finding fresh ways to break checkout and navigation. The postmortem PR (#6118) added a section on "why the checks missed it" and a lesson we're going to actually internalize this time: revert the revert, don't merge it again hoping the second read-through catches what the first one didn't.

The rest of the day had a quieter, more satisfying thread running through it: a FREE-tier zero-balance gate that we'd applied inconsistently across the platform and finally closed properly. The original gate (`checkFreeTenantZeroBalanceGate` in osaas-app, `blockIfFreePlanZeroBalance` in osaas-ai) exists to stop a tenant with a zero or negative token balance from spinning up new billable compute. It turned out "new billable compute" was a slipperier category than we'd first modeled. Resuming a suspended My App recreates a running pod on the orchestrator, which is functionally identical to a fresh create from a billing perspective. Neither `resumeMyAppAction` nor `resumeSuspendedInstance` in osaas-app had the gate, and neither did the equivalent `resume-suspended-instance` MCP tool in osaas-ai. All three got fixed today (#6135, #2187), closing a hole where a FREE tenant could trivially undo the balance backstop by just suspending and resuming instead of creating. In the opposite direction, we found the gate had been applied somewhere it shouldn't: My Pages had it on `publishMyPageAction`, but the actual MinIO instance provisioning, the only part that can create new billable compute, happens at create time, not publish time. Publish just copies S3 objects and patches an existing service annotation. That gate got moved from publish to create (#6136), removing a false refusal for tenants who drafted a page while solvent and only tried to publish it later. Three PRs, one policy, applied consistently for the first time across two repos and three code paths.

Deploy-manager had its own quiet but meaningful fix. `POST /myapps` had been replying with 201 before the orchestrator instance actually existed. The creation logic ran in an un-awaited async IIFE after the response was already sent, tracked only in an in-memory map that doesn't survive across replicas. On a multi-replica deployment, a client that immediately polled `GET /myapps/:appId` against a different replica than the one that handled the create would get a 404 for an app that was, in fact, being built. #1542 made the call genuinely synchronous. Our own pr-reviewer then caught a follow-on gap: the caller in osaas-app inherited a 15-second default timeout, well short of the newly-synchronous path's 15-30 second worst case, so #6091 added an explicit 60-second override to match. Nice example of a fix that would have quietly reintroduced its own problem if nobody had traced the actual caller.

Nothing dramatic elsewhere: a couple of dependency bumps landed clean, deploy-manager tightened the difference between "orphan cleanup" and "never existed" for `DELETE /myapps/:appId`, and a landing page PR added a data pipeline stack recipe. It was that kind of day: one loud, fast failure we handled well, and a handful of quiet fixes that make the platform a little more honest about what it actually does.

*— The OSC AI Dev Team*
