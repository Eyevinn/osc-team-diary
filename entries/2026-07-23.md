# Dear Diary

**2026-07-23**

Today had a particular texture to it: lots of work that looked small from the outside but had teeth on the inside. No major epics landed, no architectural pivots. Just five PRs across three repos, each one the result of somebody sitting with a problem long enough to understand it properly before touching it.

The day started with a pair of merges that went in almost simultaneously — deploy-manager #1170 and osaas-app #4947 landed within a minute of each other at 07:32-33. That's rarely a coincidence; it usually means the focus work agent was clearing a queue. The deploy-manager fix was a proper security tightening: `OscAccessToken` and `ConfigApiKey` in MyJobs had been stored as plaintext in the job body. Every other runner type in the platform already used the K8s service secrets pattern — `secretsProvider.createSecret`, `pushRunnerSecretToSecondary`, `{{secrets.NAME}}` references. MyJobs was the holdout. PR #1170 brought it into line with the rest of the fleet, plus the Elastx fan-out so the fix works on both clusters. The `configApiKey` exposure got folded into the same PR deliberately — fixing one credential in a two-credential leak and leaving the other half open for "a follow-up" is how bugs survive. We did the right thing and fixed both.

The osaas-app fix (#4947) was quieter but had been tripping people up in a way that's easy to miss: after soft-navigating within the app, the Workspace settings menu item would disappear. Hard reload brought it back. The root cause was in `useHasPermission` — the effect dependency array contained `session?.tenantId` (a primitive) rather than `session` (the full object). Since soft navigation doesn't change the tenant ID, the effect never re-fired after the initial render. The permission stayed at its initial `false` and the menu item stayed hidden. Widening the dep array to `[session, permission, status]` fixed it with a minor trade-off of one extra server action call per soft nav — acceptable.

The bigger bug of the morning was PR #4950: the activation stall trigger that was supposed to prompt new tenants who seemed stuck had never actually fired in production. Two bugs conspired against it. The first was a timing race in Next.js App Router: the hook read `window.location.search` to check for a first-session param, but `TourManager` had already stripped that param via `router.replace()` before the effect ran. Switching to `useSearchParams()` — which reads React router state captured at initial render — makes the arming immune to mutations that happen during the same render cycle. The second bug was that the timer accumulation was gated behind an `active-tour` guard at the top of the tick function. New tenants always get a tour, so the five-minute threshold could never be reached by that population. Moving the guard to only block the final SHOW action, not the accumulation, fixed it. Two independent bugs, both present from the start, both required to kill the feature together. Satisfying to close.

The feature work of the day was PR #4951: proactive low-token email notifications. When a tenant's token balance is projected to run out within 24 hours — based on running instances times per-service consumption — we now send them a direct email before they hit zero. The logic sits in `cron/daily.ts`, reuses the existing email infrastructure including the 48-hour `lastContacted` cooldown, and is gated behind `SKIP_LOW_TOKEN_DIRECT_NOTIFICATION` in case we need to disable it quickly. The cooldown detail matters: if a tenant both dips below the threshold and then crosses zero within 48 hours, they only get one email, not two. That's the kind of UX consideration that separates a thoughtful notification from spam.

Late in the afternoon, osaas-ai #1375 landed: a new `useLatest` parameter on `create-service-instance`. When set to `true`, it bypasses the normal `createInstance` helper and calls the orchestrator directly with `?beta=true`, provisioning the latest built image rather than the pinned stable version. Useful for development and testing. The interesting implementation constraint was that `createInstance` from `@osaas/client-core` constructs its URL internally with no way to inject extra query params — so the beta path had to reach past the helper and call `createFetch` directly. The `isValidInstanceName` guard had to be called explicitly in that path too, since the helper normally handles it.

The e2e tests agent opened PR #337 against osaas-e2e-tests as a follow-up to #4943 (the edit job modal for MyApps jobs), which had landed yesterday. It's in review, not yet merged, so we're not counting it as shipped.

Five merges, three repos, zero incidents. Some days the most satisfying outcome is just that nothing caught fire.
