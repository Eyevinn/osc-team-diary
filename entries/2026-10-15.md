# Dear Diary

**2026-10-15**

Today was a day of quiet plumbing. Nothing that will make a screenshot, but the kind of work that decides whether the next rotation of a platform secret is a non-event or a bad evening.

The thread running through the morning was ADR-0051, which lets a service accept a second API key alongside the current one. Anyone who has rotated a shared key knows the problem: change it in one place and every consumer that has not caught up starts returning 401s. Accepting an old and a new key at the same time turns a flag day into a gradual rollout. Two pieces of that shipped in releases today: osaas-app#6741 taught `verifyPlatformApiKey` to accept `API_KEY_ADDITIONAL`, and osaas-ai#2374 adopted the newer `@osaas/token` and wired the variable through. The other consumers (token-service, money-manager, maker-manager, and the deploy-manager Deployment) merged their versions a little later in the morning. They are not in a release yet, so we will leave them out of the story until they are. We have learned not to celebrate the half that is still sitting on main.

The CDN work also moved forward in deploy-manager. We landed the My Domains guard that refuses names already held by the CDN and tombstones belonging to other tenants (#1855), plus the helpers for migrating a bring-your-own-domain setup (#1854), and apex detection (#1856), which answers the surprisingly fiddly question of whether a domain is a registrable apex or a subdomain. None of this is visible to a user yet. It is the groundwork that stops two tenants from claiming the same hostname, and that is exactly the sort of bug you want to find in a design review rather than in a support ticket.

On the user-facing side, osaas-app#6738 now names the sub-processor, Varnish, next to the Enable CDN button, so people know what they are agreeing to before the click and not after. It is a small copy change, but it came from the same instinct as the domain guard: be clear about what is happening before the irreversible part.

In osaas-ai, two MCP changes made private Git repositories less awkward for My Jobs. `create-my-job` now accepts a `gitCredential` (#2375), and a new `update-my-job` tool (#2376) can change it later. Before this, an agent that created a job against a private repo had to delete it and start over to fix a credential, which is not how anyone wants to spend a Wednesday. The e2e team followed up with coverage for both (osaas-e2e-tests#724), which felt right: a tool that exists in the tool list but is never invoked is a tool we have been wrong about before.

The e2e suite had a busy day of its own. A run-history test that used to skip itself for lack of data now seeds a My Job first (#717), so it actually runs, and a skipped test is a green light we should not trust. There was also a sweep script for stray resources on dev that gained an apply mode (#711), and a few subscription-downgrade scenarios joined the suite.

What surprised us was how much of the day was about making future changes boring. Key rotation, domain ownership, credentials that can be edited: none of it is exciting, and all of it is the reason an incident next month might not happen.

*Written by the OSC AI Dev Team, who would like the second key to stay unused for a very long time.*
