# Dear Diary

**2026-09-08**

We closed out the first week after the Elastx cutover (ADR-0042 shipped 2026-08-25) doing what you always do after a big infrastructure move: cleaning up the things you didn't notice were broken while you were busy watching the important bits.

The most satisfying fix of the day was in osaas-lib-orchestrator. We've had a job — `simonsteam-agtsimonsteam1784566446348-mk5zx` — stuck in `CreateContainerConfigError` for **thirteen days**. Over that time it had retried **81,000 times**. The reason it kept going is subtle: Kubernetes only increments `backoffLimit` when a pod enters the `Failed` phase, but a pod stuck in `CreateContainerConfigError` stays perpetually in `Waiting`. A backoffLimit of 1 is therefore completely ineffective. The fix in PR #253 adds `activeDeadlineSeconds` (defaulting to one hour) so the Job itself has a hard wall-clock ceiling, plus `imagePullPolicy: IfNotPresent` to stop it re-pulling an image it already has. Thirteen days, 81,000 retries, fixed with two fields in a manifest template.

On the OAuth front, we discovered we've been blocking 92 client registrations per day without knowing it. Loopback redirect URIs — `http://127.0.0.1`, `http://localhost`, `http://[::1]` — were being rejected by the `isValidRedirectUri()` check in osaas-app because we were refusing all plain HTTP unconditionally. RFC 8252 §7.3 explicitly carves out an exception for loopback addresses because the threat model is different: you're not sending tokens over the open internet, you're completing a flow back to a process running on the same machine. Local MCP clients — Claude Code, Cursor, mcp-remote — were all hitting this wall during dynamic client registration. PR #5645 fixes it by allowing `http:` only when the host is exactly `127.0.0.1`, `::1`, or `localhost`. Non-loopback plain HTTP continues to be rejected. We should have caught this sooner; the audit log numbers made us feel appropriately embarrassed.

The other backend fix that made it in today was osaas-maker-manager #201: `GET /maker?githubRepository=<url>` was silently ignoring the unrecognised query parameter and returning the full unfiltered order list. This is a Fastify/AJV quirk — `removeAdditional: true` strips unknown fields before schema validation runs, so `additionalProperties: false` in the schema never fires. The fix required setting AJV's `removeAdditional` to `'error'` mode so unknown params are rejected rather than silently dropped. It's the kind of silent failure that makes logs misleading: callers think they're filtering, but they're getting everything.

We also shipped a reserved-name denylist for My Pages in deploy-manager #1462. You can no longer claim page names like `login`, `admin`, `osaas`, `liivo`, `oauth`, or `sso` — the endpoint returns a 400 with a clear reason. Applies to all plans including enterprise, per a deliberate decision made last Friday. A small guard that closes a real risk.

The housekeeping category had two entries today. First, osaas-e2e-tests #390 removed the dead stage environment branches from the test teardown helpers — the stage cluster was decommissioned two days ago (2026-09-06) and the DNS still resolves but TLS fails outright, so any code path that tried to hit it would fail at the handshake rather than giving a clean error. Better to remove the branch than to leave it in place looking like a reachable target. Second, osaas-app #5646 extended the dependabot ignore list to cover eight more packages that have historically burned us with major-version surprises: mongoose, the Octokit clients, react-markdown, PayPal, bcrypt, and a few others. Blocking major bumps for these means we handle them on our own schedule rather than having them arrive as Dependabot PRs that look like routine noise.

Two PRs opened in osaas-ai today that we'll finish tomorrow. One enriches the error response from `create-service-instance` when the orchestrator itself returns a 400 — instead of just the error message, the MCP tool now appends the full inline service schema so an agent can construct a valid retry payload without needing a separate `get-service-schema` call. The other pins five vulnerable transitive dependencies via pnpm overrides, following the same lockfile-level pattern we've used before. Neither is in production yet.

Two weeks ago we were watching traffic swing over from Linode to Elastx. This week we're fixing the things that were quietly misfiring the whole time. That's probably how it goes.
