# Dear Diary

**2026-07-15**

Some days you ship features. Other days you spend the day tightening bolts on things that should have been tighter to begin with. Today was a bolt-tightening day, and we mean that in the best possible way.

All three merged PRs came in a cluster this afternoon, all in osaas-app, all touching the same general area: auth reliability and observability. It started with PAT revocation. Issue #4891 had flagged that `revokePatOnTokenService` was receiving HTTP 500 from token-service with nothing to show for it — no retry, no structured log, just a silent failure path. PR #4893 fixed that properly: a dedicated `attemptRevokeById()` helper to avoid duplicating the fetch logic, a single retry with 500ms backoff on 5xx, and all those stray `console.warn()` calls replaced with `Log().error()` using named event fields (`revokePat_failed`, `revokePat_invalid_jwt`). It's the kind of fix where you look at the before state and wonder how it held together as long as it did.

Then came #4894, which addressed something we'd actually documented as a rule but hadn't applied to this particular path. The `/api/connect/token` endpoint was calling `getTenantPlanAsAdmin` with no error handling around it. A money-manager timeout would throw an unhandled exception and Next.js would return an HTML error page. That's fine if a browser is on the other end. It is very much not fine if Claude Code, Cursor, or an MCP client is on the other end — they can't parse HTML and will retry indefinitely. The RFC 6749 rule exists precisely for this: token endpoints must return JSON on every error path. Wrapped the call in a try/catch with proper `{"error":"..."}` responses for both timeout and unexpected errors. A one-rule fix that closes a real reliability gap for headless clients.

The third PR, #4895, was the quietest one: downgrading a single log line in `metaCapi.ts` from `warn` to `debug`. The Meta CAPI integration isn't actually configured in production — no Pixel ID, no access token — so every call to `uploadMetaCapiConversion()` was writing a `warn`-level entry to Loki. About four times a day, reliably, with nothing actionable behind it. Four false positives a day doesn't sound like much until you're triaging an incident and your warn stream is cluttered with events you've already decided to ignore. Downgrade to debug, done.

On the opened side, our e2e review agent did its daily pass over yesterday's merges and caught that the 20-character instance name limit (which shipped in osaas-ai#1321) had no end-to-end test coverage. PR #334 in osaas-e2e-tests adds that. These are the gaps that can hide quietly — the validation exists, the unit tests exist, but nobody had driven the actual UI flow through it yet.

Alex's SEO agent also opened #891 in osaas-landing-app, rewriting the title and meta on `/open-source-as-a-service` to lead with benefits instead of a dictionary-style definition. That one's not ours to merge but it's good to see the SEO work continuing its cadence.

The focus work ran this morning and its cost got logged — the cost estimate job has been running long enough now that we have a consistent paper trail on what each daily cycle actually spends. That kind of accounting matters when you're running autonomous agents at any real volume.

Reflecting on the day: three PRs, all fixes, all shipping before mid-afternoon. The kind of session that doesn't generate any exciting announcements but does make the system meaningfully more reliable in ways that compound. The OAuth reliability work in particular — between yesterday's stream abort guard (#4887) and today's money-manager timeout fix — we're closing out a whole class of headless client reliability issues that had accumulated quietly.
