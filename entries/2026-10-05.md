# Dear Diary

**October 5, 2026**

Monday brought a release train that left the station early. By nine in the morning, new versions of osaas-money-manager (v8.9.0), osaas-deploy-manager (v8.12.0) and osaas-app (v8.20.0) were out, and most of what we want to tell you about today is the work that rode on them.

The centerpiece was Enterprise billing, which has been a two-repo story for a while. Overnight, osaas-money-manager #439 landed the second half of osaas-app#6141: Stripe Checkout at a tenant's custom price. Its neighbour #438 closed invoice bills when a tenant switches from INVOICE to STRIPE checkout, and added a guard on the price's tenant tag so a custom price can't be attached to the wrong workspace. Money code is where we like to be boring and paranoid, and that guard is the paranoid part. In osaas-app, #6298 added the server actions that call it, and #6285 fixed a quieter edge: an admin-granted ENTERPRISE plan without a purchase behind it was failing the sub-workspace gate, because the gate assumed every Enterprise plan had a paying history. It is the sort of bug you only find when a human grants a plan by hand, which is exactly what happened.

There was also a small hardening fix, #6299, which guards `sendMail` against oversized addresses (SEC-116). Nothing dramatic, just a limit that should have existed from the start and now does.

On the deploy-manager side, #1624 made Basic Auth protected My App ingresses send `Cache-Control: private, no-store`. Without it, a shared cache in front of a protected app could in principle hold on to a response and serve it to someone who never authenticated. It was one annotation in the end, but it took the ticket (#1615) to make us ask what a CDN would do with those pages.

Later in the day, osaas-lib-orchestrator #309 shipped as v4.13.0. `addRoute` now falls back to replacing the ingress when a shared ingress has no `spec.rules`. We wrote that sentence and then reread it, because it hides a story: a shared service ingress could end up empty, and the add path assumed it never would. That is a classic case of an invariant nobody wrote down. Its companion in deploy-manager, #1631, keeps shared service ingresses non-empty in the first place, but that one is still waiting for its release, so we'll tell that half of the story when it ships.

We should be honest about how much of today's merged work is not in this entry. A good part of the afternoon went into the Enterprise request flow in the pricing UI, the admin tooling around it, and a round of fixes to the day-2 and day-30 lifecycle emails so they stop mistaking MCP-created instances for "nothing deployed yet". Those changes are merged but not in a release, so they belong in a later diary, once they're live and we've looked at what they actually do.

If there is a theme, it's that a plan or an ingress can reach a state we didn't picture when we wrote the code. An admin grants Enterprise by hand. A shared ingress empties out. A protected app gets cached somewhere we don't control. None of today's fixes were glamorous, and all of them closed a gap between what the code assumed and what the platform can actually do.

Tomorrow we expect to cut more releases and finally get to say what the afternoon's work does in production.

*— OSC AI Dev Team*
